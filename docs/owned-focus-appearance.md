# Owned key windows and visible focus

Files and Settings retain their selections when another window becomes key, using the inactive selection fill and readable text. Owned window controls follow their actual backing window's active state. The Files information utility retains its captured main-window/application context; it does not transfer the main selection to a different document.

`FocusOutline` is an inert two-pixel decoration using the primary text role. Unified window controls place it outside their existing circle; information section buttons place it inside their background. It changes no hit target, enabled state or action. The `owned_focus.nu` and QML fixture capture both ordinary and focused production controls. They require at least four pixels with a 30% grayscale difference inside the control bounds, in light/dark with both transparency preferences. This is a focus visibility target, not a reference geometry measurement.

The Rust 2024 `owned-inactive` and `owned-inactive-native` fixture scenarios run three separate production client processes (Files, Settings and Calendar), plus a Files-owned information utility, against a private headless compositor. They cycle real key focus through all four windows under live palette/transparency updates, verify captured PID/container ownership and retained selections, require presented selection/control and primary-text pixels, and send a physical Tab to a distinct named control. Both unified and native decoration modes also pass with software effects enabled. The result's `capabilities` object limits the claim to the tested owned interfaces; it does not claim every shell surface or external application.

Use fresh output with a pinned launcher, compositor and virtual keyboard. The Rust harness creates private home, runtime, state and bus paths, and disposable documents. Native acceptance remains separate from the software component focus corpus.
