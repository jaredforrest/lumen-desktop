# Shell recovery

The shell is a compositor client. Ordinary applications run independently. The user service restarts a failed shell after two seconds, with at most three starts within sixty seconds. After repeated failures, an independent recovery terminal explains how to inspect logs and manually retry the shell. It does not stop applications or restart the graphical session. The terminal service has no automatic restart and only opens when the shell reports `start-limit-hit`.

Consumers can disable the automatic terminal with `services.lumen-desktop.integrations.shellRecovery.enableFallback = false` while retaining the restart bound. `fallbackPackage` may supply a different package exposing `bin/lumen-session-recovery`.

The Rust `lumen-lifecycle-native-fixture recovery` scenario starts two actual GTK text documents, enters synthetic unsaved text with physical keyboard events, then kills the actual shell with SIGKILL while a menu and then the Dock hold keyboard input. Each restart must expose a working menu within five seconds after the explicit supervisor start. Both client process identities, compositor container identities and modified text remain; exactly two client windows are reported. Real input must work during the outage and after the recovered menu and Dock dismiss. The fixture supplies private audio and explicit unavailable unrelated hardware producers in a detached namespace. All child logs are checked after reaping.

The native fixture explicitly starts the replacement process; it does not run a systemd user manager. The compiled Rust recovery helper has a separate eight-case endpoint check covering healthy and failed statuses, malformed or unavailable status, terminal failure, instruction text and interactive-shell handoff. Test endpoints replace only the immutable status, terminal and shell executables. Production commands use the user manager explicitly and never retry automatically.

`nix build .#checks.x86_64-linux.recovery-policy-vm` exercises the real systemd user manager in a disposable software-emulated VM. The fixture derives the restart budget, fallback and session ownership policy from the public module, substitutes disposable process endpoints, and asserts the user manager's unit lookup scope before starting them. Three crashes must exhaust the budget, start a separate held recovery process and preserve an independent client process identity. Explicit reset/start must recover the shell; the recovery process must remain independent. A second service proves the disabled fallback has no handler. Stopping the graphical target must retire all session-owned processes. The serial log is retained in the check output; failed-service diagnostics are expected evidence of the injected crashes.

The VM has no host filesystem shares or external network. Software-emulated boot has a bounded 600-second outer budget; the guest's state assertions retain separate thirty-second deadlines. CI runs checks with one build job and two compiler cores so boot does not compete with other compiler jobs on its runner. These are test resource bounds, not boot-performance targets. The VM proves supervisor policy, not a real recovery terminal's appearance, physical power loss, login recovery or live-system activation. Native client-survival and endpoint tests establish their separate boundaries; none alone establishes all recovery behavior.
